# Setup & authentication (last updated: 2026-08-10)

How a fresh instance bootstraps itself and how requests are gated
afterwards. Product spec §11/§12 (first-run `/setup` wizard) and §4
(admin/member roles) are the target; this note maps what exists today.

## The `setup_done` flag

The flag lives in `organizations.settings["setup_done"]` — a string key,
because it is a JSON column. Two functions in `CodeLead.Accounts` own it:

- `setup_done?/0` — the only read. It selects `settings` directly and
  treats a missing organization as "not set up", so it is safe on an
  empty database. **Never use `get_organization!/0` for this** — it
  raises before the first run.
- `complete_setup/0` — merges `%{"setup_done" => true}` into the existing
  settings map (it does not replace it).

`priv/repo/seeds.exs` writes the flag as `true`, so a seeded dev instance
skips the wizard. `CodeLead.AccountsFixtures.organization_fixture/1`
defaults to `true` for the same reason.

## The two gates

`CodeLeadWeb.SetupGate` and the generated `CodeLeadWeb.UserAuth` stack in
that order:

1. `:browser` runs `fetch_current_scope_for_user` (session → `@current_scope`).
2. `SetupGate` sends the user to `/setup` until the instance is set up,
   and out of `/setup` once it is.
3. `UserAuth.require_authenticated_user` sends the user to
   `/users/log-in`.

Each gate has **two faces** and the router uses both: the plug covers
HTTP requests and the initial LiveView mount, the `on_mount` hook covers
live navigation *within* a `live_session`, which never re-runs router
pipelines.

### Router shape

| Scope | Pipelines | `live_session` | Routes |
|---|---|---|---|
| Wizard | `:browser, :setup_pending` | `:setup` | `live /setup`, `post /setup/admin` |
| Auth | `:browser, :setup_done` | `:current_user` | log-in / magic-link confirmation |
| App | `:browser, :setup_done, :require_authenticated_user` | `:require_authenticated_user` | `GET /`, account settings, board, task page, `/settings/*` |

The wizard sits in its own `live_session` on purpose: leaving it forces a
full page load, so the router re-evaluates the gate with the new flag
instead of live-navigating past it.

Login is behind `:setup_done` because before the wizard runs there are no
users to log in as — `/users/log-in` redirects to `/setup` too.

## The wizard

`CodeLeadWeb.SetupLive` (panels in `CodeLeadWeb.SetupLive.Steps`) walks
admin → provider → project → agent → finish.

**The current step is derived from the database on every mount**, not
tracked as navigation state. Each step commits as soon as it is
submitted, so a reload mid-wizard resumes where it left off:

| Step | Considered done when | Writes |
|---|---|---|
| `:admin` | any user exists | `Accounts.ensure_organization/1` + `Accounts.register_admin/1` |
| `:provider` | `Agents.list_providers/0` is non-empty | `Agents.create_provider/1` |
| `:project` | a project exists **or** was skipped | `Projects.create_project_with_repository/2` |
| `:agent` | `Agents.any_agents?/0` **or** was skipped | `Agents.create_agent/1` |
| `:finish` | — | `Accounts.complete_setup/0`, then `push_navigate` to `/` |

Admin and provider are required; project and agent are skippable
(product spec §11). Skips live in a `MapSet` assign and are deliberately
**not** persisted — a reload re-offers the step.

### Why the admin step posts over HTTP

A LiveView cannot write the session, and the wizard must leave the admin
logged in. So `SetupLive` validates the admin form live and then sets
`phx-trigger-action`, letting the browser POST it to
`CodeLeadWeb.SetupController.create_admin/2`, which registers the admin,
stores `:user_return_to` and calls `UserAuth.log_in_user/2`. This is the
same trick the generated `UserLive.Login` uses.

`Accounts.register_admin/1` differs from the generated
`register_user/1` in three ways: it stamps `role: :admin` **on the
struct** (never cast, so it cannot come from form params), it sets a
password directly, and it stamps `confirmed_at` — a self-hosted first run
has no mail transport, and the wizard is the trust boundary. It refuses
once any user exists.

Repository linking is transactional
(`Projects.create_project_with_repository/2`) so a rejected git URL does
not leave a half-created project behind; it returns
`{:error, :project | :repository, changeset}` so the caller can put the
errors on the right fields.

## Authentication

Generated by `mix phx.gen.auth Accounts User users --live` (Phoenix
1.8, scope-based, magic link + password, bcrypt). Deviations from the
generated output:

- `CodeLead.Accounts` keeps the organization functions and the
  profile/admin helpers (`create_user/1`, `update_user/2`,
  `change_user/3`, `delete_user/1`) alongside the generated auth API;
  `CodeLead.Accounts.User` keeps `role`, `locale` and `settings`, and its
  `changeset/2` casts neither `role` nor `password`.
- **Self-signup is closed.** `UserLive.Registration` and
  `/users/register` were removed: the wizard creates the first admin, and
  every later account comes from `/settings/users`. `create_user/1`
  supports both paths — with a `password` it sets the hash **and**
  `confirm_changeset/1` (mandatory: `login_user_by_magic_link/1` raises
  for an unconfirmed user that has a password), without one the user is
  left unconfirmed and gains access by magic link.
  `Accounts.delete_user/1` refuses the last user, since an instance with
  no users can no longer be recovered through the browser.
  `register_user/1` is retained for the test fixtures.
- **Two email token contexts reach `/users/log-in/:token`.** `"login"`
  tokens come from the login page and last 15 minutes; `"invite"` tokens
  come from `/settings/users` (create-with-invite and *Resend invite*,
  both via `Accounts.deliver_invite_instructions/2`) and last 72 hours,
  since nobody is waiting at the screen for an emailed invite.
  `UserToken.verify_magic_link_token_query/1` accepts either, each against
  its own window, so the context stamped at creation decides the lifetime
  and a login token can never borrow the longer one. Both are single-use
  and share the confirmation LiveView; invites get their own email copy
  (`UserNotifier.deliver_invite_instructions/2`).
- The generated migration was folded into
  `20260810130342_create_users.exs` (nothing was deployed at the time, and
  `create_tasks` already FKs `assignee_id → users`, so a later-timestamped
  migration would have ordered wrong). Reset with `mix ecto.reset`. That
  shortcut is no longer available — deployed instances exist, so schema
  changes now ship as new forward migrations.
- The log-in and confirmation LiveViews render inside `Layouts.auth/1` —
  a chromeless wordmark + theme toggle + centered column — instead of the
  project sidebar, and use the project's tokens rather than the generated
  daisyUI classes. The nav bar the generator injects into
  `root.html.heex` was removed in favour of `Layouts.account_card/1` in
  the sidebar. `/users/settings` is signed-in and therefore renders in the
  normal app shell like the rest of `/settings` — see
  [`navigation.md`](navigation.md).

### Known gaps

- `users.role` is stored, set and displayed, but nothing authorizes on
  it — admin and member see the same surfaces, and every signed-in user
  can manage users, providers, agents and projects from `/settings`. The
  Users page therefore shows the role read-only rather than offering a
  select that would imply enforcement.
- Sudo mode guards the account-settings page only; `/settings/*` is not
  sudo-gated.

## Testing

`CodeLeadWeb.ConnCase` creates the organization singleton (already set
up) for every web test, so the gate does not redirect the whole suite.
Tag a case `@moduletag :setup_pending` to get an empty instance and test
the wizard itself. `setup :register_and_log_in_user` logs a user in.
